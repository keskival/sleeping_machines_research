# Completed-width selection for the64K integrated stage

`aws_token_width_decision.py` compares the completed P16/P24 pair, optionally
adding P32 after its own fit and selected-checkpoint utility complete. The
current evidence has P16 only, so no wider member is selected or promoted.
Every record is immutable input evidence captured by SHA256 in the decision.

Same65,536admitted training tokens,131,056fitting presentations/two passes,
seed6,optimizer,source/data,history and evaluation cadence are required.
The entire declared initial-inclusive selection schedule must be present.
Utility must match the selected step/loss and actual target count, with route
RNG and partition parity. Pending fits and unmatched controls are rejected.

Select the lowest DEV NLL among completed members with at least0.02NLL
improvement over initialization and positive contextual utility. Ties choose
fewer parameters. The0.02learning gate is the existing program's practical
pilot gate, not statistical significance. Width changes both core features
and default decoder ranks; it does not isolate either component. More vector
width increases active arithmetic while keys and selected writes stay fixed.
It does not establish useful dormant-bank capacity at constant work.

A selected width needs seed7 replication and its actual complete fitting/
inference ledger before the next data stage. Repeat learning at seed7 is
member replication; claiming a confirmed width advantage additionally needs
its matched narrow control at seed7. The reserved256Kpoint and larger
extrapolation test remain in TOKEN_SCALING_PLAN.md. Neither the decision
script nor its tests provide a scaling exponent or public Transformer win.
